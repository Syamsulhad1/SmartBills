# Bagian 1. Identitas dan Topik Proyek Aplikasi

## Nama Aplikasi

**SmartBill — Sistem Pencatatan Keuangan Multimodal Berbasis AI Agent**

## Deskripsi Singkat dan Tujuan

SmartBill merupakan aplikasi yang dirancang untuk membantu pengguna dalam melakukan pencatatan keuangan dengan cara yang lebih praktis. Aplikasi ini memanfaatkan teknologi OCR dan AI untuk membaca informasi dari foto struk, nota, atau bukti transaksi kemudian mengubah informasi tersebut menjadi data transaksi yang dapat disimpan oleh sistem.

Ide utama dari aplikasi ini adalah mengurangi pekerjaan pencatatan yang biasanya dilakukan secara manual. Pengguna tidak perlu selalu mengetik nominal, nama transaksi, atau kategori pengeluaran satu per satu. Setelah data berhasil dibaca oleh sistem, pengguna tetap dapat memeriksa dan memperbaikinya sebelum transaksi disimpan.

Dengan demikian, SmartBill tidak hanya berfungsi sebagai tempat menyimpan catatan keuangan, tetapi juga membantu pengguna memperoleh gambaran mengenai kondisi keuangannya melalui riwayat transaksi dan rekapitulasi.

## Target Pengguna

Target pengguna SmartBill adalah mahasiswa, pekerja, masyarakat umum, serta pemilik usaha kecil yang membutuhkan cara sederhana untuk mencatat pemasukan dan pengeluaran sehari-hari.

## Teknologi Utama

Teknologi yang digunakan dalam rancangan SmartBill meliputi:

- React Native Expo untuk aplikasi mobile.
- React.js untuk dashboard web.
- Node.js dan Express.js untuk backend serta REST API.
- PostgreSQL sebagai basis data.
- Google Cloud Vision untuk proses OCR.
- Google Gemini sebagai teknologi LLM untuk membantu mengolah hasil pembacaan transaksi.

# Bagian 3. Hubungan dan Implementasi pada Topik Proyek

## 1. Bagaimana rancangan aplikasi dapat mempermudah tugas sehari-hari pengguna?

Menurut saya, masalah utama yang ingin diselesaikan SmartBill adalah kebiasaan pencatatan keuangan yang sering dianggap merepotkan. Ketika seseorang membeli sesuatu, biasanya masih ada proses lain setelah transaksi selesai, yaitu menyimpan struk, mencatat nominal, menentukan kategori, dan menghitung kembali kondisi saldo.

Jika semua dilakukan secara manual, kemungkinan pengguna lupa mencatat menjadi cukup besar. Karena itu, saya melihat foto struk sebagai sesuatu yang dapat dimanfaatkan menjadi sumber data transaksi.

Pada SmartBill, pengguna cukup mengambil foto struk atau mengunggah bukti transaksi. Sistem kemudian membaca informasi dari gambar menggunakan OCR. Hasil pembacaan tersebut selanjutnya diproses oleh AI untuk mendapatkan informasi seperti nominal, nama toko, dan kategori transaksi.

Setelah data diperoleh, pengguna tetap dapat melihat hasilnya terlebih dahulu. Jika ada bagian yang salah, pengguna dapat mengubahnya. Setelah data dianggap benar, transaksi baru disimpan ke database.

Menurut saya, perubahan yang paling terasa adalah perpindahan dari proses:

**Transaksi → menyimpan struk → menulis ulang data → menghitung saldo → membuat rekap**

menjadi:

**Transaksi → foto/upload bukti → sistem membaca → pengguna memeriksa → data tersimpan → kondisi keuangan dapat dipantau.**

Dengan cara tersebut, teknologi tidak menggantikan pengguna sepenuhnya, tetapi mengurangi pekerjaan yang berulang.

## 2. Bagaimana struktur penyimpanan file dan keamanan password dirancang?

Menurut saya, pengguna aplikasi tidak perlu mengetahui bagaimana file sebenarnya disimpan di server. Yang penting bagi pengguna adalah mereka dapat menemukan bukti transaksi dengan mudah.

Karena itu, pada SmartBill saya membayangkan file bukti transaksi dikelompokkan berdasarkan akun pengguna dan waktu transaksi. Misalnya, transaksi bulan September dapat ditampilkan pada halaman riwayat bulan September. Pengguna cukup memilih transaksi tertentu untuk melihat bukti foto yang berkaitan dengan transaksi tersebut.

Di belakang sistem, penyimpanan dapat menggunakan struktur berdasarkan ID pengguna, tahun, dan bulan sehingga file milik pengguna yang berbeda tidak tercampur.

Contoh konsep penyimpanannya:

```text
storage/
└── user/
    └── user_id/
        └── 2026/
            └── 09/
                ├── transaksi_001.jpg
                ├── transaksi_002.jpg
                └── transaksi_003.jpg
```

Untuk keamanan akun, saya akan menerapkan aturan password yang tidak mudah ditebak. Saat pengguna membuat akun, aplikasi dapat memberikan informasi mengenai tingkat keamanan password dan memberikan peringatan apabila password terlalu sederhana.

Saya juga menilai bahwa password tidak seharusnya disimpan dalam bentuk asli di database. Password perlu diproses menggunakan mekanisme hashing sebelum disimpan.

Untuk komunikasi antara aplikasi dan server, sistem juga perlu menggunakan HTTPS. Sementara autentikasi API dapat menggunakan JWT sehingga server dapat mengetahui apakah request berasal dari pengguna yang sudah melakukan autentikasi.

## 4. Bagaimana penerapan etika digital dan AI yang bertanggung jawab?

SmartBill pada dasarnya merupakan aplikasi pencatatan keuangan pribadi sehingga interaksi antar pengguna bukan bagian utama dari aplikasi. Karena itu, risiko seperti trolling atau cyberbullying tidak menjadi fokus utama sistem saat ini.

Namun, jika suatu saat ditambahkan fitur yang memungkinkan pengguna berbagi informasi atau berinteraksi, menurut saya perlu terdapat mekanisme seperti report, block, pengaturan privasi, dan aturan penggunaan.

Untuk AI, saya berpendapat bahwa pengguna tidak boleh langsung percaya terhadap hasil AI tanpa pemeriksaan. AI dapat mengalami kesalahan ketika membaca foto, terutama jika gambar buram, pencahayaan kurang, atau format struk berbeda dari biasanya.

Karena itu, alur yang saya anggap lebih aman adalah:

```text
Foto Struk
    ↓
OCR
    ↓
AI memproses data
    ↓
Hasil transaksi ditampilkan
    ↓
Pengguna memeriksa
    ↓
Pengguna memperbaiki jika diperlukan
    ↓
Transaksi disimpan
```

Dengan alur tersebut, pengguna tetap menjadi pihak yang menentukan apakah data transaksi sudah benar.

Menurut saya, AI pada SmartBill sebaiknya diposisikan sebagai alat bantu untuk mengurangi pekerjaan manual, bukan sebagai pihak yang mempunyai keputusan akhir atas data keuangan pengguna.

## 5. Data PII apa saja yang perlu dilindungi?

SmartBill berhubungan dengan data keuangan sehingga perlindungan data menjadi bagian yang sangat penting.

Data yang mungkin berkaitan dengan pengguna antara lain:

- Nama pengguna.
- Alamat email.
- Informasi autentikasi.
- Data pemasukan dan pengeluaran.
- Saldo.
- Riwayat transaksi.
- Foto struk atau bukti transaksi.

Foto struk juga perlu dianggap sebagai data yang perlu dijaga karena dalam kondisi tertentu dapat mengandung informasi lain, misalnya nama seseorang, informasi toko, atau bagian tertentu dari bukti pembayaran.

Menurut saya, prinsip yang perlu diterapkan adalah hanya mengumpulkan data yang benar-benar diperlukan oleh aplikasi. Jika sebuah fitur tidak membutuhkan suatu data, maka data tersebut tidak perlu diminta dari pengguna.

Perlindungan data dapat dilakukan melalui beberapa cara, seperti:

1. Menggunakan HTTPS untuk komunikasi aplikasi dengan server.
2. Menggunakan autentikasi JWT untuk request API.
3. Melakukan hashing terhadap password.
4. Membatasi akses data berdasarkan akun pengguna.
5. Menjaga API key dan credential agar tidak dimasukkan ke kode yang dapat diakses pengguna.
6. Tidak menampilkan data pengguna lain.
7. Menjaga file bukti transaksi agar hanya dapat diakses oleh pemiliknya.

Selain perlindungan teknis, pengguna juga perlu diberikan pemahaman mengenai phishing. Aplikasi sebaiknya tidak meminta pengguna memberikan password melalui pesan atau link yang tidak jelas.

## 6. Bagaimana aplikasi mengomunikasikan masalah teknis kepada pengguna?

Menurut saya, pesan error merupakan bagian penting dari pengalaman pengguna. Pesan seperti:

```text
500 Internal Server Error
```

memang berguna bagi developer, tetapi tidak banyak membantu pengguna biasa.

Karena itu, SmartBill sebaiknya menerjemahkan masalah teknis menjadi pesan yang mudah dipahami sekaligus memberikan pilihan tindakan.

### Contoh 1 — Koneksi Internet Bermasalah

> **Koneksi internet tidak tersedia**
>
> SmartBill belum dapat mengirim transaksi ke server.
>
> Silakan periksa Wi-Fi atau data seluler Anda, kemudian coba kembali.
>
> **[Coba Lagi]**

### Contoh 2 — Foto Struk Tidak Terbaca

> **Foto struk belum dapat diproses**
>
> Tulisan pada foto mungkin terlalu kecil, buram, atau kurang cahaya.
>
> Coba ambil foto kembali dengan pencahayaan yang lebih baik dan pastikan seluruh struk terlihat.
>
> **[Foto Ulang] [Input Manual]**

### Contoh 3 — Data Belum Dapat Dimuat

> **Data belum berhasil dimuat**
>
> Server belum memberikan data terbaru. Periksa koneksi internet atau coba beberapa saat lagi.
>
> **[Muat Ulang]**

Menurut saya, pola pesan error yang baik adalah:

**Masalah → penyebab sederhana → tindakan yang dapat dilakukan.**

Dengan pola tersebut, pengguna tidak hanya diberitahu bahwa sistem mengalami masalah, tetapi juga diberikan arahan untuk mencoba menyelesaikannya sendiri. Konsep ini berhubungan dengan Modul 6 yang membahas troubleshooting secara bertahap.

Ketika konsep tersebut saya hubungkan dengan proyek SmartBill, saya melihat bahwa teknologi yang digunakan dalam aplikasi harus tetap memperhatikan pengguna. AI dapat membantu membaca dan mengolah transaksi, tetapi hasilnya tetap perlu diperiksa. Data keuangan harus dilindungi, pencarian harus dibuat mudah, dan ketika terjadi kesalahan sistem harus memberikan penjelasan yang dapat dipahami pengguna.

Dari keseluruhan materi, saya memahami bahwa membuat aplikasi bukan hanya tentang membuat fitur dapat berjalan. Sebuah aplikasi juga perlu mempertimbangkan bagaimana pengguna berinteraksi dengan sistem, bagaimana data mereka dilindungi, bagaimana informasi digunakan, dan bagaimana sistem membantu pengguna ketika terjadi masalah.

Menurut saya, penerapan Digital Awareness pada SmartBill dapat membuat aplikasi tidak hanya berfungsi secara teknis, tetapi juga lebih aman, mudah digunakan, dan bertanggung jawab terhadap data penggunanya.
